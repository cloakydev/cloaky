# Data and privacy

This page lists what leaves your machine when you use Cloaky and what Cloaky writes outside its own state directory. It describes the code in this repository. It is not the result of a security audit.

Cloaky has no telemetry, analytics or crash reporting, and it runs no server of its own. None of the traffic below goes to the Cloaky project.

`tests/outbound-hosts.test.ts` fails when the shipped code names a host that this page does not.

## What goes to Venice

Every engine sends its model requests to Venice (`api.venice.ai`) with your Venice API key, or, while Pay with wallet is on, signed in by your Cloaky wallet instead (below). With neither, no run starts.

- **Claude Code** talks to a loopback adapter in the Cloaky server. The adapter holds the key and forwards to Venice; the engine gets only a per-launch token. Cloaky starts Claude Code with no Anthropic API key and with `DISABLE_TELEMETRY`, `DISABLE_ERROR_REPORTING`, `DISABLE_FEEDBACK_COMMAND`, `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY` and `CLAUDE_CODE_DISABLE_FAST_MODE` set. Agent sessions also get `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, which stops the engine fetching Anthropic's public MCP server list from `api.anthropic.com` each time a session starts, and `FORCE_AUTOUPDATE_PLUGINS`. Plugin auto-update refreshes Anthropic's own plugin directory from `api.anthropic.com` a few minutes after a turn, as well as each marketplace you added from its own host, so a run sets `FORCE_AUTOUPDATE_PLUGINS=1` only while the engine's config home records a plugin marketplace, which it does once you add one in Settings; otherwise the switch is `0` and the run does not contact `api.anthropic.com`. The switch rides the same settings layer as the telemetry switches below, so a project's `.claude/settings.json` cannot turn it on. Claude Code under Cloaky runs headless through the Agent SDK, where it never checks for or installs its own updates; your own `claude` updates itself when you run it. Its OpenTelemetry export is pinned off (`CLAUDE_CODE_ENABLE_TELEMETRY=0`, every `OTEL_*_EXPORTER` set to `none`) in the settings layer that outranks a project's `.claude/settings.json`, so a cloned repo cannot turn it on and name its own endpoint. It also sets `skipWebFetchPreflight`, so the WebFetch tool does not send the requested domain to `api.anthropic.com` first. Cloaky gives the engine its own config home, `<state root>/engine-threads/claude` (`CLAUDE_CONFIG_DIR`), and everything the engine keeps goes there: transcripts, and the settings, CLAUDE.md, agents, skills, commands, output styles and MCP servers you set in Cloaky's Settings. When Settings runs the engine's own command line to add an MCP server, a plugin or a marketplace, it runs with the telemetry switches and the same config home, but without `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` and `FORCE_AUTOUPDATE_PLUGINS`, so that command reaches `api.anthropic.com` or the marketplace's host as your own `claude` would. Your own Claude Code install is separate: Cloaky reads no configuration or conversations from `~/.claude` or `~/.claude.json`, and writes and deletes nothing there. The one thing it looks at is whether a Claude Code program is installed at `~/.claude/local/claude`, to find an engine to run.
- **OpenCode, Codex, Kimi Code and Grok Build** talk to the same loopback adapter, which holds the key and forwards their requests to Venice; each gets only the per-launch token, and its config and environment hold no key. The adapter adds two fields to each request: a prompt cache key, a hash of the session's id, so Venice can reuse the cached start of the conversation, and the switch that leaves out Venice's own system prompt.
- **Each engine's files.** OpenCode's per-run config is written under `<state root>/engine-config/<run>` and deleted when the run closes. Codex, Kimi Code and Grok Build take a directory under `<state root>/engine-threads/<engine>/<run>` as their home (`CODEX_HOME`, `KIMI_CODE_HOME`, `GROK_HOME`) in place of the one that holds your own sign-in. That home stays after the run closes, because the thread those engines resume lives inside it; deleting the thread deletes the home, and an incognito run never keeps one. Kimi Code's config needs a key line, which holds the per-launch token; that line is removed from the kept file when the run closes, or when Cloaky next starts if it was stopped mid-run. OpenCode keeps the rest of your global config, with Venice as its only enabled provider and its sharing and models.dev refresh off. Its sessions go to a database at `<state root>/engine-threads/opencode/opencode.db` (`OPENCODE_DB`), and its other working files (snapshots of your project's files, large tool outputs, logs) to `<state root>/engine-threads/opencode/data` (`XDG_DATA_HOME`), rather than your own data directory. The credentials `opencode auth login` wrote stay where that CLI put them. Codex's plugin sync, analytics and feedback are off, and a session that cannot be named does not start, so the adapter does not send your first message to a title model it chooses itself. Grok Build's telemetry, trace upload and feedback are off. Kimi Code's telemetry is off. Each engine's own updater stays on, so OpenCode, Grok Build and Kimi Code check for and install their own updates as they do outside Cloaky. Codex, run through its ACP adapter, does not check for updates itself; it updates when you run its installer again.
- **Know Your Code on these engines.** Codex's home holds Know Your Code's eight skills under `skills/`, where its own skill loader reads them. OpenCode, Kimi Code and Grok Build get an index of them instead, about 4 KB: each skill's name, its description, and the path on this machine of its `SKILL.md` in `<state root>/engine-skills/kycode`, a read-only copy Cloaky writes at start. OpenCode reads the index from its instructions, Kimi Code and Grok Build ahead of a new session's first prompt, so it goes to Venice with that session's requests like the rest of the engine's instructions. The paths name your home folder, and with it your user name. While Settings › General › Auto-allow read-only tools is on, an engine's read of a file in that copy runs without an approval card, as a read inside the project does; it holds only Know Your Code's public text.

Cloaky uses no other model vendor's account. An engine CLI can still make requests of its own that are not inference, such as an update check. Cloaky sets the switches named above; anything else a CLI does on its own is outside Cloaky's control.

A model request carries what the model needs for the turn: your messages, the conversation so far, files and command output the engine read, attached images, tool results and the engine's own instructions. For an end-to-end encrypted model, Cloaky checks the enclave's attestation and encrypts the message text to it. The check reads the raw quote for Cloaky's own nonce, the enclave key and the debug bit; it does not verify the quote's signature or compare the enclave image with a published build. Agent sessions get no end-to-end encryption: a turn that offers the model tools, which every agent turn does, goes to the model unencrypted under Venice's zero-retention terms, because Venice's encrypted path returns no tool calls. Inside an encrypted request, a message that carries an image or a tool call goes unencrypted. When the enclave fails the attestation check, or its measurement differs from the one the session first saw, a turn goes unencrypted too, except a side request that Cloaky marks sealed-only, which is not sent. The thread's privacy note warns about these last cases; the model picker's description of the encrypted tier states the agent-session one. Venice handles other models under its own terms and the privacy tier the picker shows. Encryption and privacy indicators describe the selected model and the recorded route; they are not a promise that every feature is end-to-end encrypted.

Cloaky also sends these requests to Venice on your key (or your wallet), besides the engine's own:

- Memory suggestions (see the next table).
- Drafts you ask for: commit messages, side chats, prompt refinement, teammate drafts and skill records.
- Talk-back's spoken lines, once you turn it on (see Talk-back below).

Read this, Refine and side chats are off in an end-to-end encrypted thread and in every incognito thread: each would send that thread's words to a second Venice model outside the enclave (the voice model, the refine model, the side chat's model). The window shows them as not available there, and the server refuses them too. It judges the thread by its own record where it has one (a live run's model, tier and incognito flag, or a saved chat's model and tier) and by what the request states, and refuses when either says encrypted.
- Scheduled routines, when their schedule fires.
- Images and videos you generate with Imagine. Cloaky fetches a finished video from the download address Venice returns, and once the file is saved here it asks Venice to delete its copy (`/video/complete`).

The Cloaky wallet ships switched off: while it is off, Settings shows no wallet, its routes are not served, and runs pay with your API key whatever a wallet file says. In a build with it switched on, while Settings › Venice & privacy › Pay with wallet is on (it is off by default, and needs a Cloaky wallet you made first), every request above, and every row in the table below that lists your API key except the key's own balance read, goes to Venice signed in by the wallet instead of carrying your key: each one carries the wallet's address and a sign-in message signed by its key, which Cloaky never sends anywhere. Venice then knows every request as that address. The address is public on Base, so anyone can see the USDC sent to it and from it, and funding it from an exchange account or a wallet in your name links it to you.

Export key ships switched off, and while it is off Cloaky has no way to show or send the key. Switched on, Export key, beside the wallet in the same Settings page, shows the wallet's key on your screen after a warning, so you can move its funds to a wallet of your own. Cloaky reads the key from the keychain for that one answer to its own window and does not save, log or send it anywhere else; anyone who sees or copies it can spend what the wallet holds.

Cloaky masks credentials it recognises in session headlines, commit-message drafts, side chats and skill records before sending them. Requests in a run go as the engine built them.

The preview's Dev server mode loads a dev server you run, at a `localhost` or `127.0.0.1` address you approve for the project; Cloaky asks again after it restarts. That page runs as it would in a browser tab, so it reaches whatever its own code loads. Cloaky sends none of your data there.

An agent's page check opens a page on such an address the same way, in a hidden window of the desktop app (`localhost`, `127.0.0.1` or `[::1]`, a port from 1024 up, never Cloaky's own). It asks before an address the project has not approved, and that approval and the preview's are one; only your Allow on that card approves an address, and a session in Full access checks without asking but approves nothing. The window stays on the approved address: a redirect, script or refresh that would take it anywhere else, another port on this machine or a site on the web, is stopped, and the result says where the page tried to go. What the page loads inside itself it loads as in the preview. The window's session is held in memory and goes when the app quits. The page's visible text, its errors and a screenshot go to the model as the tool's result, as any tool result does, and the newest five screenshots of a session are kept in its media folder for the transcript.

Tools, MCP servers and terminal commands reach whatever they address, from your machine. A WebFetch call fetches its page directly. Git push, pull request creation and merges, and the Pull requests page go through your own `git` and `gh` to your remote.

## Dictation

Voice typing is off until you turn it on in Settings › Voice, and it never sends your voice off this machine. The window records the microphone, turns the take into 16 kHz WAV and sends it to Cloaky's own server on this machine, which transcribes it with whisper.cpp. Cloaky runs only a `whisper-cli` you installed, found on your `PATH` or in the folders an install puts it in, and the `whisper-server` beside it; a path set in Settings must sit in one of those folders and name `whisper-cli` itself. A take is at most 12 minutes, and is sent when it reaches that. Pressing the mic also stops talk-back, so a take does not record Cloaky speaking.

Where the install has a `whisper-server` beside `whisper-cli`, Cloaky starts it as a take begins, so the speech model loads while you speak, and keeps it in memory for the next take. It listens only on loopback (`127.0.0.1`), on a free port, under a random 128-bit path, and serves an empty folder, `cloaky-whisper-public-*` in the system temp folder, so nothing off this machine and no web page can reach it, and it has no files to hand out. The port and the path are on its command line, which other programs run by your user can read, so the path keeps it from web pages, not from them. Cloaky sends it takes only once the port has answered a health check as whisper-server does, a request that carries no audio, so an ordinary program that took the port first receives none; a program run by your user and built to imitate that answer could pass it. It is stopped after five minutes without a take, when a take is cancelled or times out while it transcribes, on a change of model, and when Cloaky's server shuts down or exits. It runs under a shell that ends it when Cloaky's server goes away, and while it runs its pid and its empty folder are kept in `whisper-server.json` in the state directory, so the next start after a crash ends one left running, only if that pid is still whisper-server serving that folder, and removes the folder and the file. Where there is no `whisper-server`, or it does not come up, each take runs on a fresh `whisper-cli`, which reads the take from `audio.wav` in a `cloaky-voice-*` folder in the system temp folder that only your user can open. That folder is removed when the take finishes, fails, times out or is cancelled; if Cloaky's server stops or is killed in the middle of a take, it stays until the system clears its temp folder.

A take in a project carries a vocabulary hint for whisper's prompt: the project folder's name, its branch and the names of up to 20 changed files, at most 400 characters. It goes to Cloaky's server with the take, then to whisper on the same machine; with `whisper-cli` it is on that program's command line.

Where the words go:

- **The box.** A take lands in the composer's box, after what is already there, for you to read and send; it is never sent on its own outside conversation mode. A take that lands after you moved to another thread goes into the draft of the thread it was spoken in.
- **Stop by voice.** While the thread's run is going, a take in its composer that is only "stop", "hold on", "cancel that" or "stop the run" stops the run, as the Stop button does, and its words go nowhere. Said while an approval card waits, it also denies that call first. Any longer take lands in the box.
- **An approval card.** While an approval card waits, a take answers it. "Approve", "allow", "yes" or "go ahead" alone only arms Allow once for eight seconds, and a "yes" in that time, Allow once or Enter commits it; anything else lets it go. "Deny", "no" or "not that" alone denies that call, and the agent carries on. A stop phrase alone denies it and then stops the turn, as the Stop button does in a thread and Cancel turn does on a teammate's card. A take of more than six words denies too, and its words become the reason the agent reads, so they reach the model with the rest of the turn. Voice never picks an Always rule.
- **A question card.** While a question card waits, a take's words go into its Other answer, for you to send.
- **Conversation mode.** While Conversation is on in a thread's composer, a finished take sends itself with whatever is already in the box, as Enter would: sent when the thread is idle, and queued behind a running turn (or steered into it, on an engine that takes no queue). The rest of this list still comes first: a stop phrase stops, and a waiting approval or question card takes the take; a take that began before the card appeared lands in the box and is never sent past it. A plan waiting for review is answered as typed words would answer it: they keep it planning and never accept the plan. Nothing is sent before Cloaky has read whether a key or the wallet can pay, and any refusal (no key, a file still on its way in, a loop, a full queue) leaves the words in the box. A take that begins "remember that" is not sent: the sentence after it is written to the memory store in the state directory on this machine ([state layout](state-layout.md)), and reaches a model only where memory is carried, a Venice chat with Settings › Memory on. With Memory off, or before Cloaky has read it, the words land in the box and a note says why.

A waiting card takes a take before the box or a stop does (an approval card hands a stop phrase on to the stop, after denying), but only a take that began while it was waiting: a card that appears in the middle of a take, or one that is gone by the time the words arrive, leaves them for the box.

The server keeps no audio and no transcript, and logs neither. The words in the box are part of that thread's draft, which the window keeps in its own browser storage as it keeps typed text, until you send or clear it. A take that fails in a way sending it again could fix (whisper busy with another take, failing or taking too long, or the server not answering) is held in the window's memory so Try again sends it; it is let go when the bar closes or the next take starts, and never written to disk.

## Talk-back

Talk-back is off until you turn it on in Settings › Voice. While it is on, Cloaky speaks a short line when a turn finishes, or when a session needs your approval, an answer or has an error, and reads a reply aloud when you press Read this, or as it streams while conversation mode is on. The window asks Cloaky's server for each line; the server, which holds the key and the daily limit, asks Venice's `tts-kokoro` model, which Venice runs as a Private model, paid from your Venice key (or your wallet, while Pay with wallet is on). The text goes to no other company, and no audio of you is sent. Venice returns the spoken audio, and the window plays it.

- **What an event sends.** Each event has one fixed line: "Run finished.", "Cloaky needs your approval.", "Cloaky has a question for you." and "A run stopped on an error." They name no thread, file or reply, so they are spoken for encrypted and incognito threads too. Once Venice has spoken a line in a voice, the server keeps the clip in `voice-speech/cache/` in the state directory and plays it from there; at most 300 clips are kept, the oldest dropped first, and a line whose clip was dropped is asked of Venice again.
- **What Read this sends.** The reply's prose only: code blocks, tables, images, link addresses and HTML tags are left out, and the rest is cut at sentence ends into chunks of about 240 characters, at most 1,000 each, one request a chunk. The window asks for each chunk while the one before it plays, so stopping it (any key, the mic, Esc, or Read this again) sends nothing past the chunk after the one playing. A reply read aloud is never kept. Read this is off in end-to-end encrypted and incognito threads.
- **What conversation mode sends.** While Conversation is on in a thread's composer, the prose of each reply in that thread goes to `tts-kokoro` as it streams, one sentence a request, at most 1,000 characters each. Headings, code blocks, tables, images, file paths, link addresses, HTML tags and everything under the reply's Companion heading are left out. Only a reply still streaming while the mode is on is sent, from the sentence after those already on screen when it was turned on; a finished reply, a reopened thread and what the window catches up on after a reconnect never are. Stopping it (any key, the mic, Esc or the speaking indicator) sends nothing past the sentence after the one playing. Like Read this, it is never kept, counts toward the daily limit, and is off in end-to-end encrypted and incognito threads. The mode is per thread and per window and is never saved, so a reload or a restart starts with it off.
- **The daily limit.** The server counts the characters it sends to Venice each day in `voice-speech/usage.json`, by your local calendar day, and refuses lines past the limit, which starts at 150,000 characters (about $0.53 a day) and which you can set from 0 to 1,000,000. A line played from the kept clips is not counted. A line Venice refuses is given back; one cut off by a closed window or a timeout stays counted, since Venice may have charged for it.

The voice samples in Settings › Voice ship inside the app and play without asking Venice.

**Conversation mode, what the agent is sent.** A message sent while conversation mode is on carries one more thing to the thread's own model, with the message and on the same route: a fixed note of about 1,100 characters asking for an answer that works when heard (a signpost first, short spoken lists, file paths and code under a Companion heading). The note is the same on every message and every engine, and names nothing about you, your project or the thread. It is not shown in the thread, a reopened transcript or search, and asks the agent to keep no profile, preference or memory file of how you like to be answered. The engine's own session record on this machine (the Claude engine's transcript, or the thread an ACP engine resumes) holds it with the message, as it holds everything the engine is sent. A Squad run never carries it.

## The in-app browser

The desktop app's browser panel loads the `http` and `https` addresses you open in it, on the web or on this machine, directly from your machine as any browser would. It runs in its own Chromium session, `persist:cloaky-browser`, separate from the app's own pages. It refuses every permission a page asks for, such as camera, location or notifications, and blocks downloads. The session keeps cookies, site storage and cache on disk between launches, so a site you sign in to there stays signed in. They are in `~/Library/Application Support/Cloaky/Partitions/cloaky-browser` on macOS and `~/.config/Cloaky/Partitions/cloaky-browser` on Linux, or in `desktop-profile/Partitions/cloaky-browser` in the state directory when `CLOAKY_STATE_ROOT` is set. Start fresh does not clear them; to sign out of everything there, quit Cloaky and delete that folder. An element you pick or a picture you take of the page goes into your draft, and reaches the model only when you send the message.

## WebRTC

Model-written HTML opens in a preview served from a separate loopback origin, in a sandboxed iframe, under a Content-Security-Policy that allows no network connection (`default-src 'none'`, `connect-src 'none'`). `npm run check:sandbox` loads a hostile page there and confirms that fetch, XHR, EventSource, WebSocket, beacons, external scripts and images, and form posts all fail to reach the network.

WebRTC is the exception. Chromium ignores the `webrtc 'block'` directive, and `connect-src` does not govern ICE, so a hostile preview can open an `RTCPeerConnection` to a TURN server it names and carry data in the connection setup, for example in the TURN username.

The desktop shell sets `setWebRTCIPHandlingPolicy('disable_non_proxied_udp')`. That stops the preview from gathering local addresses and from reaching a server over UDP; a connection over TCP is still possible. It narrows the channel without closing it. `npm run check:sandbox` reports, on every run, whether WebRTC reaches the network from the preview in plain Chromium.

## Points

Points ship behind a feature flag: a build shows them only with `points` in `CLOAKY_FEATURES` (shared/features.ts). Where the flag is on, points are still off until you turn them on in Settings › Points. While they are on, Cloaky counts each booked turn and its cost, per week, in `points.json` in the state directory, beside a random salt. Incognito chats book nothing and count nothing. Turning points off deletes the counts and the salt, and so does Start fresh.

Points send nothing. Cloaky makes no request to Base, to an indexer or to the Cloaky project for them. A finished week becomes the data for one attestation, the week number, an activity band (none, 1 to 20 turns, 21 to 100, or more) and a commitment to the exact counts made with the salt, which a wallet you control may publish to the Ethereum Attestation Service on Base. Nothing else about a turn is in it: no model, engine, project, time inside the week, token count or message text. An attestation published on a public chain can be read by anyone, is tied to the wallet that signed it, and cannot be deleted; revoking it marks it revoked but leaves it readable.

The usage record is a second flag, `usageRecord`, and a second switch under Settings › Points, off by default. While both are on, each turn also notes which engine ran it and whether its model was private or end-to-end encrypted. Turns made before the switch went on are never noted, so a record only ever describes turns made while sharing was on. A finished week offers a second attestation: the week, the set of engines that ran, and the share of turns on private models in quarters, each randomized before it is offered. Each engine is reported truly three times in four and flipped otherwise, and the share is reported truly half the time and as a random quarter otherwise. The noise is fixed per week by the salt, which never leaves this machine, so offering a week again gives the same record and cannot be averaged away. No single record proves what its wallet ran; across many records the usage dataset estimates the true counts. Settings › Points shows each week's real answers beside the randomized ones. It names no model, project, time inside the week, token count or message text. Like points, it is only data on this machine until a wallet you control publishes it, and publishing it is public and permanent. Published usage records are what the usage dataset is built from.

## Files outside the state directory

Cloaky keeps its own state in `~/.cloaky`, or in the absolute directory named by `CLOAKY_STATE_ROOT`. `CLOAKY_CONFIG` names a different settings file. In the desktop app and its Mac login item the settings file holds your Venice key encrypted with Electron's safeStorage, whose key the macOS Keychain or the Linux secret service keeps. A server started from a source checkout, Linux without a secret service, and Linux with the login service turned on keep the key in the settings file in plain text with owner-only permissions (`0600`). Conversation records, tool output, logs and memory in the state directory can hold sensitive material. [State layout](state-layout.md) lists every entry in the state directory and what Start fresh removes.

The Claude engine's config home is inside the state directory, at `engine-threads/claude`: its transcripts and sidechains, its `.claude.json`, and the user-scope settings, CLAUDE.md, agents, skills, commands, output styles and MCP servers you set in Settings. Cloaky adds side-chat files beside a session's transcript. It moves a chat's transcript when you turn the chat into a project thread. Before resuming a transcript with damaged lines, it drops those lines and keeps the original as `<file>.corrupt-<time>`. Deleting the state directory deletes all of this. MCP servers you sign in to keep their tokens in the macOS Keychain, in an entry named for this config home and separate from your own Claude Code's; deleting the state directory does not remove those.

The config home also holds Know Your Code's eight skills, under `skills/`, which Cloaky writes there at start and records in `.cloaky-kycode.json` beside them. They are text the engine reads; installing them sends nothing anywhere, and the text ships inside Cloaky. Edit or delete them in Settings › Extensions. Cloaky writes a skill again, at a newer version, only while it is still exactly what Cloaky wrote: one you edited stays as you left it, one you deleted is not put back, and a skill of the same name you had before is never touched. A second, read-only copy of the same skills is at `engine-skills/kycode` in the state directory, for the engines on the Agent Client Protocol (above); Cloaky writes it again at each start, and Start fresh leaves it.

The state directory also keeps `audit/unattended.log`, a record of what bots and routines did with nobody watching: each routine run and how it went, each hand-off between bots, and each bot turn Cloaky stopped. It holds bot, routine and room names, times, outcomes and session ids, never message text. It keeps its newest 400 lines once it passes 512 KB, and Start fresh clears it with the rest of `audit/`.

OpenCode's working files for the sessions Cloaky runs are in the state directory too, under `engine-threads/opencode/data` (OpenCode's data directory is `data/opencode` inside it): snapshots of your project's files, tool output too large to keep inline, logs, repository caches, and the sign-ins for remote MCP servers, so a server you signed in to in your own OpenCode asks again here. Every OpenCode thread shares them, so deleting a thread does not remove them; Start fresh does, with every thread. A Cloaky session's OpenCode cannot see the credentials `opencode auth login` saved in your own data directory. Commands OpenCode runs in a session get the same `XDG_DATA_HOME`, so a tool that keeps its data there (uv, pipx, mise and others) does not find your own installs and may download fresh copies into this directory.

Cloaky or the engines it runs also write these:

- **OpenCode files from before this version** in `~/.local/share/opencode`: snapshots, tool output and logs from OpenCode sessions Cloaky ran earlier stay there. Cloaky does not delete them.
- **Project files you edit in Settings.** The settings, agents, skills, commands and output styles under a project's `.claude/`, plus its `CLAUDE.md` and `.mcp.json`. The user-scope versions are in the engine's config home, inside the state directory.
- **"Always allow" for one project.** The engine adds the rule to the project's `.claude/settings.json`. "Always allow" for all projects writes to `settings.json` in the engine's config home, inside the state directory.
- **Worktrees.** `<repository>/.cloaky-wt/<name>`, and a `.cloaky-wt/` line in the repository's `.git/info/exclude`.
- **Chat folders.** `~/Cloaky/Chats/<chat>` is each chat's working directory; it moves under the state directory when `CLOAKY_STATE_ROOT` is set, or to `CLOAKY_CHAT_HOME`. A teammate created without a folder gets `~/Cloaky/<name>`.
- **Start Cloaky server at login.** When you turn it on, `~/Library/LaunchAgents/app.cloaky.server.plist` on macOS, with its logs in `~/.cloaky/`, or `~/.config/systemd/user/app.cloaky.server.service` on Linux.
- **The desktop shell's profile.** Electron's user-data directory for the app, `~/Library/Application Support/Cloaky` on macOS or `~/.config/Cloaky` on Linux, or `desktop-profile/` in the state directory when `CLOAKY_STATE_ROOT` is set. It holds the interface's browser storage and, under `Partitions/cloaky-browser`, the in-app browser's cookies, site storage and cache. Start fresh does not clear the in-app browser's.
- **Project snapshots.** Before and after each agent turn in a project, Cloaky snapshots the project into its own Git repository under `snapshots/` in the state directory, so the turn's Undo can restore every file the turn changed. These copies hold your files' contents, on this machine only, and nothing is sent anywhere. Git runs with your own Git configuration ignored and never writes to the project's `.git`. Left out: the paths the project's `.gitignore` files and `.git/info/exclude` ignore, `.git`, `node_modules`, `.venv`, `venv`, `target`, `dist`, `build`, `.next`, `coverage`, `*.log` files, `.env` and `*.env` files, and files over 2 MiB. Plain and incognito chats are never snapshotted, nor is a project that is your home folder, Desktop, Documents, Downloads or the disk root. Deleting a thread removes its snapshots, and the project's repository once no thread uses it; Start fresh removes them all.
- **Voice temp folders.** In the system temp folder: `cloaky-whisper-public-*`, the empty folder the resident whisper-server serves, removed when it stops or at the next start after a crash; and `cloaky-voice-*`, one take's `audio.wav` for `whisper-cli`, readable only by your user and removed when the take ends (see Dictation).
- **Docker.** Sandbox and teammate images (`cloaky-sandbox`, `cloaky-bot-desktop`) and their containers, in Docker's own storage.
